## 这节课你会...

听懂"工具调用"和"MCP"这两个总被人挂在嘴边的词，以及它们跟你有什么关系。

## 大模型只会写字

先把最大的误会拆掉：大模型本身只会干一件事，接着往下写字。

它不能查天气，不能看你的日历，不能给谁发邮件。它只会输出一串文字。

那为什么你让它查天气，它真能给你天气？因为**外面有人给它配了手**。它写出一句"我要查天气"，程序看见这句话，就去调用真正的天气接口，再把结果塞回来，它接着往下写。

所以"AI 会动手"这个说法不太准。准确的说法是：**AI 说话，程序做事，AI 再看着结果往下说。**

## 工具调用，用大白话讲一遍

这个机制一般叫 function calling，工具调用。流程就这么几步：

1. 你问它："明天要穿外套吗"
2. 它判断需要天气数据，于是输出一句约定好的话："调用天气查询，城市=我这儿，日期=明天"
3. 程序看见这句，去查，拿到"明天 8 到 15 度，有风"
4. 程序把结果给它
5. 它看着结果，写出人话："明天最低 8 度，风不小，外套带上"

关键在第 2 步：**它只是"点名"要用哪个工具，真正去查的是程序。** 它自己碰不到任何东西。

这套机制的解释器、工具清单、参数，都是做产品的人配好的，你作为用户看不见。你只要记住一件事：**一个 AI 能不能帮你办某件事，取决于有没有人给它做好了对应的工具。** 没人做，它就只能嘴上说说。

想知道你手上那个助手到底有哪些工具，可以直接问：

```
我想让你帮我【查一下明天学校图书馆开不开门】。

你先别直接回答，按这个顺序来：
1. 说清楚答这件事你需要哪些信息
2. 说清楚你手上有没有能查到它的工具
3. 如果没有，告诉我该去哪儿查，或者教我把什么数据贴给你
4. 我贴给你之后，你再用它来回答
```

它老实说"我没有这个工具"，比它硬编一个答案有用得多。

## MCP 是个什么约定

工具调用有个麻烦：每个产品都要为每个工具单独对接一次，接一次改一次，很累。

MCP 想解决的就是这个。它是一套大家商量好的约定，规定"工具怎么介绍自己""结果怎么传回来"。谁按这套约定做，谁就能被接上。

一个常见的比方：**它像 USB-C。** 以前每个牌子一个接口，出门得带一把线。现在统一了，一根线插哪都行。MCP 起的就是这个作用，只不过统一的不是充电口，是 AI 接工具的那一端。

所以你会看到很多产品都说自己支持 MCP。支持的意思是：**别人做好的 MCP 服务，它能接过来用。** 至于能接的多不多、好不好用，各家差得远，以你实际用的那个为准。

## 这对普通学生意味着什么

往远了看，这件事挺实在。

现在的 AI 助手基本只知道你当场跟它说的话。以后它可能连上你的笔记、日历、网盘、课程平台。你问一句"我这周有什么要交的"，它自己去几个地方查一遍，汇总给你。

| 现在 | 以后（有的已经能了） |
|---|---|
| 你手动把课表贴给它 | 它自己读你的日历 |
| 你复制一段笔记问它 | 它自己翻你的笔记库 |
| 你把 PDF 传给它 | 它自己从网盘里拿 |

不过得泼盆冷水：**这套东西现在还不好配。** 折腾半天连不上的情况很常见，能接的服务其实也没那么多。想尝鲜可以，别指望一步到位。

## 连 MCP 有风险，这条得记住

这点比上面所有内容都重要。

你接一个别人做的 MCP 服务，本质上是**把你的一部分权限交出去**。它能读你的笔记，就有机会读你全部笔记；它能发消息，就有机会用你的名义发消息。

风险有这么几种：服务是别人写的，你不知道它背后干了什么；你给它的权限可能比它真正需要的多；这些服务更新频繁，今天没问题不代表明天没问题。

几条能落地的做法：

- 只连你自己信得过的来源，别从乱七八糟的地方抄个链接就装
- 给权限的时候，只给这件事真正需要的那点，能读就别给写
- 第一次连上，先拿不重要的一份资料试，别直接开你整个网盘
- 不用的服务记得删掉，留着就是留着一个口子

真要连之前，先问它一遍：

```
我准备把【某个 MCP 服务】接给你用，功能是【读我的笔记】。

你先说清楚三件事：
1. 接上以后，你能看到我的哪些东西
2. 你会在什么情况下主动去读它
3. 如果这个服务只能给我只读权限，会少掉哪些功能

不确定的地方就说不知道，别猜。
```

> 记住这一句：AI 自己不会动手，是工具让它动的手。谁给的手、那只手能碰到什么，才是你真正要盯的地方。
